# 自动化小说内容生成结构设计

> 面向长篇网文（100章以上，持续更新型），完全从零生成，输入仅为类型和热点触发词。

---

## 一、核心挑战

长篇从零生成面临三种必然发生的熵增，所有结构设计都围绕对抗这三点：

| 问题 | 表现 | 本质 |
|------|------|------|
| **故事漂移** | 写到第50章，人物性格和第1章悄悄不一样 | 状态层失效 |
| **情节注水** | 没有外部压力时AI自然填充无意义过渡 | 节奏控制缺失 |
| **伏笔遗忘** | 第10章埋的线，第80章没人记得要收 | 伏笔账本缺失 |

这三个问题不是 prompt 质量问题，是结构性问题，只能用结构性手段解决。

---

## 二、信息分层模型（L0-L3）

内容生成依赖四层信息，每层稳定性和粒度完全不同：

```
L0  类型基因层     初始化时生成，之后只读
L1  全书骨架层     初始化时生成，关键节点前可小幅修订
L2  滚动状态层     每章更新，核心是防止漂移
L3  当章执行层     每章临时构建，生成完即丢弃
```

### L0 类型基因层

从热点提炼出这本书的底层驱动逻辑，写死后不再改变。

```yaml
爽点机制: 碾压型 / 反转型 / 积累型 / 虐→甜型
主角弧线: 从弱到强 / 始终强 / 身份隐藏型
感情线权重: 无 / 辅助线 / 并行线
节奏基调: 快节奏爽文 / 慢热权谋 / 情绪流
```

作用：给所有后续生成提供风格约束，AI 在写第99章时仍然知道这本书的爽点机制，不会自己变成另一种类型。

### L1 全书骨架层

不是详细大纲，是故事的承重墙——拆掉任何一块整本书就塌了的内容。体积控制在 300 字以内。

```yaml
核心矛盾: 主角最终要解决的根本问题（不是"打败反派"，是"为什么非打不可、打完后世界怎么变"）

主角弧线: 从[初始状态]到[终态]，中间经历了什么根本性改变

四个锚点:
  触发点:    第X章，发生了什么让故事正式开始
  不归点:    第X章，主角做了什么或遭遇了什么，再无退路
  最低谷:    第X章，主角最接近失败的时刻
  终局触发:  第X章，什么条件激活最终冲突

反派逻辑: 反派的目标 + 为什么他认为自己是对的
```

### L2 滚动状态层

整个系统最关键也最难做好的层。分三个子层，更新频率不同：

**高频状态（每章更新）**

```yaml
scene:
  location: 当前场景
  time: 故事内时间点
  atmosphere: 紧张/轻松/压抑

characters:
  - name: XX
    location: XX
    goal_now: 这章之后的当前目标
    emotion: 情绪状态
    knows: [目前掌握的关键信息]
    doesnt_know: [目前不知道但对情节有影响的信息]
```

**中频状态（每5-10章更新）**

```yaml
relationships:
  - pair: [A, B]
    status: 敌对/信任/暗中观察
    last_changed: 第X章

power_balance:
  - faction: XX势力
    current_strength: 强/弱/消亡
    recent_change: 发生了什么
```

**低频状态（关键节点时更新）**

```yaml
foreshadows:
  - id: f001
    planted: 第X章
    content: 埋了什么
    status: 未揭示
    deadline: 最晚第X章必须揭示

secrets:
  - content: 什么秘密
    who_knows: [知道的角色]
    who_doesnt: [不知道但对情节有影响的角色]
```

**状态更新机制**：不能只靠 AI 读文章提取，必须在生成章节时同步强制输出结构化变更单，用变更单驱动数据库更新：

```json
{
  "character_updates": [
    {"name": "XX", "location": "京城", "knows": ["XX的真实身份"]}
  ],
  "world_updates": [],
  "foreshadow_updates": [
    {"id": "f003", "status": "revealed"}
  ]
}
```

### L3 当章执行层

每章生成前由系统临时构建，不存储，用户不可见：

```
从第三层大纲取本章任务
从 L2 提取当前涉及角色的状态
检查伏笔账本有无快过期的伏笔
构建上文摘要（上章结尾150字以内）
组装成完整生成指令包
```

## 三、多层大纲结构

大纲分四层，每层粒度、稳定性、用途完全不同：

```
第一层  全书脊梁     1份      整本书只生成一次        → 对应 L1
第二层  卷级大纲     3-5份    按故事阶段划分          → 中期规划
第三层  章节序列     滚动     提前规划15-20章         → 近期规划
第四层  场景指令     单章     生成前临时构建           → 对应 L3
```

### 第一层：全书脊梁

即 L1 全书骨架层，内容见上。用户可查看，不建议直接修改。

### 第二层：卷级大纲

按主角处境的根本性变化切卷，不按字数平均分。

每卷字段：

```yaml
卷名: （内部用）
章节范围: 第X章 - 第X章
本卷核心任务: 这一卷结束时世界/角色状态怎么变了
本卷爽点类型: 主打什么类型的爽点
本卷情感基调: 紧张/轻快/压抑/热血
引入的新元素: [新角色/新势力/新信息]
本卷末钩子: 结尾留什么悬念
与下卷衔接: 遗留什么问题，下一卷接手什么
```

典型五卷结构参考：

| 卷 | 阶段 | 主角处境变化 |
|----|------|-------------|
| 第一卷 | 建立世界+触发冲突 | 从"不知道危险"到"被迫卷入" |
| 第二卷 | 初入局+第一次失败 | 开始行动，遭遇真正阻力 |
| 第三卷 | 蓄力+最低谷 | 资源积累，遭遇最大挫折 |
| 第四卷 | 反攻+真相揭露 | 主动出击，核心秘密曝光 |
| 第五卷 | 终局+收束 | 最终对决，所有伏笔兑现 |

### 第三层：章节序列（滚动规划窗口）

只维护未来15-20章，写完5章向前滚动补充新的5章。

每章条目：

```yaml
chapter: 23
type: 爆发章          # 铺垫 / 蓄力 / 爆发 / 过渡

plot_task:
  what_happens: 这章发生的核心事件
  result: 章末世界状态

character_task:
  focus: [XX, YY]
  change: XX对YY的态度从敌意变为警惕

payoff_task:
  has_payoff: true
  type: 打脸           # 打脸/实力展示/反转/情绪释放
  setup: 哪几章的铺垫在这章兑现

hook: 章末留什么悬念

foreshadow:
  plant: [这章埋什么伏笔]
  reveal: [这章揭示什么，对应哪个伏笔ID]
```

**节奏配比硬约束**（写在规划逻辑里，不依赖 AI 自觉）：

```
每10章内：
  铺垫章 ≤ 3章
  连续蓄力/铺垫 ≤ 4章
  爆发章 ≥ 2章
  相邻爆发章间隔 ≥ 3章

每20章：至少1个大爆发章（强度比普通爆发高一级）
```

### 第四层：场景指令

即 L3 当章执行层，内容见上。

### 四层联动规则

```
生成顺序：
  第一层 → 第二层 → 第三层前15章

写完一章触发：
  更新 L2 状态层
  检查第三层后续章节是否需要调整

写完5章触发：
  滚动补充第三层新的5章
  检查是否接近卷末，是则提前生成下一卷第二层大纲

每20章自动校准：
  对比第一层锚点 vs 实际进度
  检查伏笔账本过期风险
  输出调整建议，修订第三层窗口
```

### 大纲双轨存储

用户编辑的和系统执行的是同一份大纲的两种形态，互相转换，用户不感知。

**用户看到的（自然语言）：**
```
第23章
XX在城门外偶遇YY，两人第一次正面交锋。
XX用账本里的证据逼得YY当众哑口无言，围观者才意识到XX不是草包。
章末，YY的随从悄悄跟上了XX……
```

**系统存储的（结构化YAML）：** 即第三层章节条目格式。

**编辑权限分级：**

```
自由编辑：   情节内容、角色变化方向、章末钩子
需提示范围：  章节类型（破坏节奏配比时警告）、伏笔揭示安排
不建议改：   第一层核心矛盾和四个锚点（改这个等于换了一本书）
```

## 四、资产管理

### 资产分类

小说生成过程中产生的所有可复用信息统称为"资产"，分为三类：

**静态资产**（初始化后基本不变）

```
角色卡       姓名/外貌/性格底色/能力/口头禅/绝对不会做的事
世界规则     力量体系/社会规则/物理约束/禁忌
势力图谱     各势力名称/实力/立场/与主角的关系
地点库       关键场景的氛围、空间结构、特殊属性
```

**动态资产**（随故事推进持续更新）

```
角色状态快照    当前位置/目标/情绪/掌握的信息（每章更新）
关系网络        角色间关系的当前值（每5-10章更新）
势力格局        各势力当前强弱（关键事件后更新）
伏笔账本        所有伏笔的埋设/状态/过期时间
秘密分布图      谁知道什么，谁不知道什么
```

**生成产物**（章节内容本身）

```
章节全文        正式写入的章节内容
章节摘要        每章100字以内的内容摘要（供后续召回用）
章节元数据      章节类型/涉及角色/发生事件/状态变更单
```

### 资产生命周期

```
初始化阶段：
  生成静态资产（角色卡/世界规则/势力图谱）
  初始化动态资产（初始状态快照/空伏笔账本）

每章生成后：
  写入生成产物（全文/摘要/元数据）
  执行变更单 → 更新动态资产
  检查伏笔账本过期状态

每5-10章：
  压缩过期的高频状态（保留关键信息，丢弃细节）
  更新关系网络和势力格局

定期维护：
  归档已完结的伏笔条目
  压缩过长的角色状态历史
  清理不再出场角色的高频状态
```

### 资产压缩策略

随着章节增加，动态资产会持续膨胀。需要主动压缩，防止 context 越来越臃肿。

```
压缩时机：
  单个角色状态历史超过N条时，压缩为摘要
  已揭示的伏笔条目归档，不再进入召回
  超过20章未出场的角色，高频状态降级为静态快照

压缩原则：
  保留"当前最终态"，压缩"变化过程"
  保留"对未来情节有影响的信息"，丢弃"已完成使命的信息"
  压缩后的版本必须能支撑角色重新出场时的一致性
```

## 五、内容向量召回结构

### 为什么需要向量召回

长篇生成过程中，并非所有历史信息都需要每次全量带入 context（成本极高且引入噪音）。向量召回的作用是：**按需提取当前章节生成真正需要的历史内容片段**。

### 向量化对象

不是所有内容都值得向量化，按优先级：

```
必须向量化：
  每章摘要（100字以内，描述本章核心事件）
  角色关键事件（影响角色状态的重要时刻）
  伏笔记录（埋设时的原文描述片段）
  世界规则条目（每条规则独立向量化）

按需向量化：
  重要对话片段（涉及关键信息的对白）
  场景描写片段（特定地点的氛围描写，供风格一致性参考）

不需要向量化：
  章节全文（太长，召回精度差）
  高频状态（用结构化查询更准确）
  角色卡全文（直接带入 context 更可靠）
```

### 召回触发时机

并非每章生成都需要全量召回，按场景触发：

```
构建 L3 当章执行层时触发召回：

  1. 涉及角色的历史行为召回
     → 查询：[角色名] 的关键事件
     → 用途：确保角色行为逻辑一致，防止性格漂移

  2. 当前场景的历史描写召回
     → 查询：[地点名] 的场景描写
     → 用途：保持场景氛围和细节一致

  3. 待揭示伏笔的原始描写召回
     → 查询：伏笔账本中 status=未揭示 且本章需揭示的条目
     → 用途：揭示时保持与埋设时的呼应

  4. 相似情节的历史章节召回
     → 查询：与本章 plot_task 语义相近的历史摘要
     → 用途：防止情节重复，确保每次冲突有新意

  5. 风格参考召回（可选）
     → 查询：同类型爽点章节的摘要
     → 用途：写爆发章时参考历史爆发章的节奏
```

### 召回结构设计

```
索引结构：

  chapter_summary_index
    向量：章节摘要的 embedding
    元数据：chapter_id / type / characters[] / events[]

  character_event_index
    向量：角色关键事件描述的 embedding
    元数据：character_name / chapter_id / event_type / impact

  foreshadow_index
    向量：伏笔埋设描写的 embedding
    元数据：foreshadow_id / planted_chapter / status / deadline

  world_rule_index
    向量：世界规则条目的 embedding
    元数据：rule_id / category / related_characters[]

  scene_description_index
    向量：场景描写片段的 embedding
    元数据：location / chapter_id / atmosphere
```

### 召回策略

**混合召回**（语义 + 结构化过滤结合）：

```
不要纯语义召回：
  "写第50章，召回所有相关内容" → 结果太宽泛，噪音多

正确做法：先结构化过滤，再语义排序

示例：召回XX角色的历史行为
  Step 1: 结构化过滤
    WHERE character_name = 'XX'
    AND chapter_id < current_chapter
    AND event_type IN ['决策', '冲突', '情感变化']

  Step 2: 语义排序
    对过滤结果按与当前章节任务的语义相似度排序

  Step 3: 截断
    取 Top-K（通常3-5条），不要全量返回
```

**召回结果的使用方式**：

```
不直接把召回内容塞进 prompt
而是提炼成约束条件：

召回到：第12章XX曾经答应过YY不会主动出手
提炼为约束：[本章约束] XX不能主动攻击YY，除非YY先出手

召回到：第8章描写过这个山洞"潮湿、布满青苔、有滴水声"
提炼为约束：[场景一致性] 保持山洞的潮湿阴暗感，不要写成干燥空旷
```

### 向量库维护

```
写入时机：每章生成完成后，异步写入（不阻塞下一章生成）

更新策略：
  章节摘要：不可变，只增不改
  角色事件：追加新事件，不修改历史事件
  伏笔记录：状态字段更新（未揭示→已揭示），向量不变
  世界规则：有修订时重新向量化，旧版本标记为过期

清理策略：
  已揭示的伏笔：保留索引，降低召回权重
  已消亡势力/角色：标记为归档状态，不再参与主动召回
  超过50章的章节摘要：降低权重，只在明确指定时召回
```

## 六、从热点到第一章：完整生成路径

```
输入：一个热点词/梗/人名

Step 1  热点解析
        提炼情绪标签（爽/虐/搞笑）
        匹配最适合的爽点机制
        生成2-3个故事方向（每个一句话，具体可感）

Step 2  用户选方向
        唯一需要用户决策的地方

Step 3  生成 L0 类型基因
        确定驱动逻辑、主角弧线、感情线权重、节奏基调

Step 4  生成 L1 全书骨架 / 大纲第一层
        核心矛盾、四个锚点、初始角色张力
        反派逻辑

Step 5  生成大纲第二层（卷级大纲）
        按第一层锚点切卷，生成3-5卷结构

Step 6  初始化静态资产
        角色卡（主角+核心配角+反派）
        世界规则
        势力图谱
        地点库

Step 7  初始化 L2 滚动状态层
        角色初始状态快照
        空的伏笔账本
        初始关系网络

Step 8  规划大纲第三层（前15章章节序列）
        按节奏配比分配章节类型
        每章分配 plot/character/payoff 任务

Step 9  构建第1章 L3 执行层
        组装当章指令包

Step 10 生成第一章

进入滚动生成循环
```

## 七、设计原则总结

| 原则 | 说明 |
|------|------|
| **分层隔离** | 不同稳定性的信息放不同层，不混用 |
| **结构化更新** | 状态更新靠变更单驱动，不靠 AI 事后提取 |
| **滚动规划** | 大纲只提前规划15-20章，不过早锁死细节 |
| **节奏硬约束** | 章节类型配比写在逻辑里，不依赖 AI 自觉 |
| **按需召回** | 向量召回先结构化过滤再语义排序，结果提炼为约束条件 |
| **主动压缩** | 定期压缩动态资产，防止 context 膨胀 |
| **双轨存储** | 大纲对人展示自然语言，对机器存结构化数据 |
| **校准机制** | 每20章自动对比骨架与实际进度，防止漂移 |
