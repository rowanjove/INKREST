## 改进一：确定性质量门禁层（P0）

### 现状

你的质量检查链路是：AuditorAgent（LLM 判断）→ audit_schema.py（JSON 结构校验）→ 敏感词扫描。LLM 说"风险低"就直接通过，没有任何确定性验证。

### 目标

在 Auditor 之后、敏感词扫描之前，插入一个**纯 regex + 数据库交叉查询**的验证层，不走 LLM，结果可复现、可审计。

### 具体实现

#### 1.1 padding_guard（防灌水检测）

新增文件 `novel_agent/quality/padding_guard.py`，实现 5 种检测模式：

**模式 A：重复解释检测**
- 对正文按句号/感叹号/问号分句
- 提取每句的 2-4 字中文词集合
- 相邻 3 句的词集合交集 > 3 词 → 判定为重复解释
- 权重：5 分/次，上限 25 分

**模式 B：空洞内心戏检测**
- 匹配包含心理动词的句子：`他(知道|明白|意识到|觉得|感觉|想起|想到|感到|认为)`
- 检查该句前后各 1 句是否包含物理动作动词（走/跑/拿/放/看/站/坐/蹲/劈/搬/推/拉）
- 前后均无动作 → 判定为空洞内心戏
- 权重：3 分/次，上限 20 分

**模式 C：对话回音检测**
- 提取连续的引号对话对：`"[^"]{15,80}"`
- 对相邻两段对话提取 2-4 字中文词集合
- 词集合重合度 > 5 → 判定为对话回音
- 权重：4 分/次，上限 15 分

**模式 D：低增量段落检测**
- 按自然段分割
- 检查每段是否包含：动作动词、对话引号、感知动词、转折词、变化标记
- 以上均无 → 判定为低增量段落
- 超过 5 个低增量段落后，每多一个 +2 分，上限 25 分

**模式 E：尾部总结检测**
- 取正文最后 400 字
- 匹配总结信号词：`总之|总而言之|总的来说|从此以后|他知道.*了|她明白.*了`
- 命中 → 直接 +15 分

**评分与判定：**
- 0-20 分：none（通过）
- 21-40 分：warning（通过，记录警告）
- 41-60 分：review（通过，标记需人工审查）
- 61+ 分：fail（拦截，不允许入库）

#### 1.2 anti_ai_style_gate（反 AI 腔检测）

新增文件 `novel_agent/quality/anti_ai_style.py`，检测 10 种中文 AI 写作特征：

| 序号 | 模式 | 正则 | 说明 |
|------|------|------|------|
| 1 | 不是A而是B | `不是.{1,10}而是.{1,10}` | 典型 LLM 对比句式 |
| 2 | 那一刻明白 | `那一刻.{0,5}(终于|猛然|突然)?明白` | 顿悟模板 |
| 3 | 从未想过 | `(她|他|我)从未想过` | 常见开头套路 |
| 4 | 他意识到 | `(他|她|我)意识到` | 过度使用的心理描写 |
| 5 | 这意味着 | `这意味着` | 解释性插入语 |
| 6 | 像一座/一尊 | `像一(座|尊|个).{1,8}(一样|般|似的)` | 比喻懒惰 |
| 7 | 沉默了几秒 | `沉默了.{1,3}秒` | 节奏填充 |
| 8 | 是她的救赎 | `是(她|他|我)的救赎` | 网文 AI 腔标志 |
| 9 | 硬科学引用 | `(公式|方程|热力学|量子|熵|牛顿)` | 不该出现在网文里 |
| 10 | 学术论文腔 | `通过.{2,15}实现了|基于.{2,15}进行了` | 论文摘要句式 |

**判定标准：**
- 0 处命中：perfect
- 1-2 处命中：pass（通过，记录）
- 3+ 处命中：fail（拦截）

## 改进三：连续性 Hooks 提取增强（P1）

### 现状

你的 ContinuityCheckerAgent 是纯 LLM 判断，没有确定性的 hooks 提取。LLM 可能会遗漏细节。

### 目标

在 ContinuityCheckerAgent 之前加一个 regex 预检层，先用正则提取上章结尾的关键 hooks，再把这些 hooks 作为上下文注入到 LLM 检查中。

### 具体实现

新增文件 `novel_agent/quality/hooks_extractor.py`：

```python
import re

# 未完成动作
ACTION_HOOKS = re.compile(
    r'(正要|准备|打算|决定|即将|就要|刚想|刚准备|开始|试图).{0,15}(?:[。！？\n]|$)'
)

# 感知发现
PERCEPTION_HOOKS = re.compile(
    r'(发现|察觉|注意|看出|感觉到|意识到|听到|闻到|看到).{0,20}(?:了|到|出)'
)

# 伤势状态
INJURY_HOOKS = re.compile(
    r'(受伤|流血|伤口|疼痛|晕|昏迷|中毒|发热|发冷|虚弱|透支|内伤|经脉)'
)

# 省略号/疑问结尾
SUSPENSE_HOOKS = re.compile(
    r'(?:\.{3,}|……|[？?])\s*$'
)

# 地点变化
LOCATION_CHANGE = re.compile(
    r'(来到|进入|走出|到达|飞往|传送至|回到).{0,15}(?:[。！？\n]|$)'
)

def extract_hooks(text: str, tail_chars: int = 400) -> dict:
    """从上章结尾提取 hooks"""
    tail = text[-tail_chars:] if len(text) > tail_chars else text

    return {
        "unfinished_actions": ACTION_HOOKS.findall(tail),
        "perceptions": PERCEPTION_HOOKS.findall(tail),
        "injuries": INJURY_HOOKS.findall(tail),
        "suspense_endings": bool(SUSPENSE_HOOKS.search(tail)),
        "location_changes": LOCATION_CHANGE.findall(tail),
        "keywords": _extract_keywords(tail)  # 2-4 字中文词
    }

def check_continuity(prev_hooks: dict, current_head: str, head_chars: int = 600) -> dict:
    """检查本章开头是否承接了上章 hooks"""
    head = current_head[:head_chars]

    results = {
        "hook_coverage": 0.0,
        "missing_hooks": [],
        "forgotten_states": [],
        "location_conflict": False
    }

    # 检查每个 hook 类型的关键词是否在开头出现
    total_hooks = 0
    matched_hooks = 0

    for hook_type, values in prev_hooks.items():
        if hook_type == "keywords" or not values:
            continue
        for keyword in values:
            total_hooks += 1
            if keyword in head:
                matched_hooks += 1
            else:
                results["missing_hooks"].append({"type": hook_type, "keyword": keyword})

    if total_hooks > 0:
        results["hook_coverage"] = matched_hooks / total_hooks

    return results
```

### 集成方式

在 ContinuityCheckerAgent 的 prompt 前，先调用 `extract_hooks()` 获取 hooks 列表，然后作为结构化上下文注入：

```
上章结尾检测到以下待承接要素：
- 未完成动作：[正要拔剑, 准备离开]
- 感知发现：[发现洞口有异光]
- 伤势状态：[左臂受伤]

请检查本章开头是否合理承接了以上要素，逐项给出判断。
```

## 改进四：场景增量验证（P2）

### 现状

你检查场景数量是否 >= 4，但不检查每个场景是否有实质推进。一个场景可以写了 800 字但什么都没发生。

### 目标

新增 scene_delta 检查，确保每个场景至少在 2 个维度上有推进。

### 7 个增量维度

| 维度 | 关键词检测 | 说明 |
|------|-----------|------|
| plot（情节） | 发现\|揭露\|得知\|出现\|发生\|遭遇\|获得\|失去 | 新事件/发现 |
| character_state（角色状态） | 决定\|改变\|选择\|放弃\|接受\|觉醒\|突破 | 角色决策/变化 |
| relationship（关系） | 信任\|怀疑\|背叛\|结盟\|爱上\|仇恨\|和解\|反目 | 关系变化 |
| conflict（冲突） | 战斗\|对峙\|威胁\|追杀\|逃离\|对抗\|击败\|受伤 | 冲突升级 |
| worldbuilding（世界观） | 规则\|法则\|禁制\|秘境\|势力\|宝物\|功法 | 世界观扩展 |
| reader_promise（承诺） | 承诺\|发誓\|约定\|复仇\|报恩\|欠下 | 爽点铺垫 |
| next_hook（钩子） | 然而\|但是\|忽然\|突然\|没想到\|谁知\|岂料 | 悬念设置 |

### 场景分割逻辑

用以下正则识别场景边界：
- 时间转换：`第二天|次日|天亮|天黑|黎明|黄昏|入夜|三日后|半月后`
- 地点转换：`来到|进入|走出|回到|飞往|离开|到达`
- 显式分隔：`***|---|***`

### 判定标准

- 单个场景：至少激活 2 个维度 → 有效场景
- 整章：有效场景数 >= 3（短章 >= 1），低增量场景不超过 1 个

### 集成位置

在 StitchEditor 之后、StyleEditor 之前执行。如果检测到无效场景，注入到 StyleEditor 的反馈中，要求补充情节推进。

## 改进五：版本不可变快照（P2）

### 现状

你用 YAML 快照做状态存档（`state/snapshots/chapter_XXX/`），但没有版本号概念。重写后旧版本被覆盖。

### 目标

新增 `chapter_versions` 表，每次 ingest 自动创建版本快照，支持回滚和对比。

### 数据库设计

```sql
CREATE TABLE IF NOT EXISTS chapter_versions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    chapter_id TEXT NOT NULL,
    version_no INTEGER NOT NULL,
    title TEXT,
    content TEXT,
    word_count INTEGER,
    status TEXT DEFAULT 'draft',    -- draft/expanded/revised/checked/final
    change_reason TEXT,
    created_at TEXT DEFAULT (datetime('now'))
);
```

### 集成方式

在 `sqlite_store.py` 中新增方法：

```python
def create_version(self, chapter_id: str, title: str, content: str,
                   word_count: int, status: str = "draft",
                   change_reason: str = "") -> int:
    """创建章节版本快照，返回版本号"""
    # 查询当前最大版本号
    row = self.conn.execute(
        "SELECT COALESCE(MAX(version_no), 0) FROM chapter_versions WHERE chapter_id = ?",
        (chapter_id,)
    ).fetchone()
    next_version = row[0] + 1

    self.conn.execute(
        "INSERT INTO chapter_versions (chapter_id, version_no, title, content, word_count, status, change_reason) "
        "VALUES (?, ?, ?, ?, ?, ?, ?)",
        (chapter_id, next_version, title, content, word_count, status, change_reason)
    )
    self.conn.commit()
    return next_version
```

在 orchestrator.py 的 ingest 步骤中调用：

```python
# 重写时记录原因
change_reason = "audit_high_risk_rewrite" if is_rewrite else "initial_generation"
store.create_version(chapter_id, title, content, word_count, status="draft", change_reason=change_reason)
```

### 前端展示

在 ChapterDetail.vue 中增加"版本历史"面板：
- 版本列表（版本号、状态、字数、变更原因、时间）
- 版本对比（diff 视图）
- 回滚按钮

## 改进六：迭代预算保护（P3）

### 现状

你的流水线没有 token 预算管理。如果在长篇生成过程中 token 耗尽，可能在 Step 14（向量索引）或 Step 15（仪表盘）时中断，导致状态不一致。

### 目标

在 orchestrator 中加入 token 计数和分级降级逻辑。

### 5 级预算区间

| 剩余预算 | 模式 | 行为 |
|---------|------|------|
| > 50% | 正常 | 全流程执行 |
| 30-50% | 收缩 | 跳过 Dashboard 更新（Step 15），跳过向量索引（Step 14） |
| 15-30% | 收尾 | 只执行 State Update（Step 13），其余跳过 |
| < 15% | 冻结 | 保存 checkpoint，输出交接方案，停止执行 |
| < 8% | 只读 | 不执行任何写入，仅输出当前状态摘要 |

### 实现方式

在 `pipeline.py` 中新增：

```python
class BudgetTracker:
    def __init__(self, estimated_total_tokens: int):
        self.total = estimated_total_tokens
        self.used = 0
        self.checkpoints = []

    def record(self, tokens_used: int):
        self.used += tokens_used

    @property
    def remaining_ratio(self) -> float:
        return max(0, 1.0 - self.used / self.total)

    @property
    def mode(self) -> str:
        ratio = self.remaining_ratio
        if ratio > 0.5: return "normal"
        if ratio > 0.3: return "shrink"
        if ratio > 0.15: return "wrap_up"
        if ratio > 0.08: return "freeze"
        return "readonly"

    def should_skip(self, step: str) -> bool:
        """根据当前模式判断是否跳过某步骤"""
        skip_map = {
            "shrink": ["dashboard", "vector_index"],
            "wrap_up": ["dashboard", "vector_index", "style_editor", "chapter_summary"],
            "freeze": ["all"],  # 保存 checkpoint 后停止
            "readonly": ["all"]
        }
        steps_to_skip = skip_map.get(self.mode, [])
        return step in steps_to_skip or "all" in steps_to_skip
```

在 OpenAILLM 的调用日志中已有 token 统计，只需在 orchestrator 中汇总即可。

## 改进七：卷桥报告（P3）

### 现状

ManagingEditorAgent 按弧线分章，但没有"卷"的概念。长篇超过 30 章后，跨弧线遗忘是常见问题。

### 目标

在弧线边界生成桥接文档，下一弧线的第一章必须引用。

### 实现方式

**Step 1：标记卷边界**

在 ManagingEditorAgent 的输出中增加 `volume_break` 标记：

```json
{
    "arcs": [
        {"name": "入门篇", "chapters": [1, 8], "volume": 1},
        {"name": "成长篇", "chapters": [9, 18], "volume": 2},
        {"name": "高潮篇", "chapters": [19, 25], "volume": 3}
    ]
}
```

**Step 2：卷结束时生成桥接报告**

在 orchestrator 的 `run_novel()` 中，检测当前章节是否为卷的最后一章。如果是，调用 VolumeBridgeAgent（可复用 ChapterSummaryAgent 的逻辑扩展）：

```python
def generate_volume_bridge(self, volume_chapters: list, volume_no: int):
    """生成卷桥接报告"""
    bridge = {
        "volume_no": volume_no,
        "ending_state": {
            "characters": self.store.list_characters(),
            "open_threads": [t for t in self.store.list_threads() if t["status"] != "closed"],
            "open_promises": [p for p in self.store.list_promises() if p["status"] == "open"],
            "open_foreshadows": [f for f in self.store.list_foreshadows() if f["status"] == "open"]
        },
        "unresolved_hooks": self._extract_unresolved_hooks(volume_chapters),
        "next_volume_requirements": {
            "must_acknowledge": [],  # 下卷必须承接的要素
            "can_abandon": [],       # 可以放弃的线索
            "tone_shift": ""         # 情绪基调变化建议
        }
    }
    # 写入文件
    with open(f"workspace/volume_{volume_no:02d}_bridge.json", "w") as f:
        json.dump(bridge, f, ensure_ascii=False, indent=2)
    return bridge
```

**Step 3：下卷首章注入**

ChapterPlannerAgent 在规划下卷第一章时，自动读取桥接报告，将 `must_acknowledge` 注入到 `must_include` 中。
