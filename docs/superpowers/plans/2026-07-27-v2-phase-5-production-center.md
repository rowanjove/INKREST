# V2 Phase 5：生产中心、审校与故障恢复重构计划

> 日期：2026-07-27  
> 分支：`codex/v2-refactor`  
> 范围：生产工作区读模型、任务队列与事件历史、质量问题归一化、修章闭环、费用与日志，以及旧监控/维护页面收敛。

## 目标

把目前分散在项目概览、日志中心、章节维护、批量状态横幅、任务日志、质量报告和费用卡片中的生产信息统一成一个生产中心：

1. 正文进度、活跃任务、阻断、质量与费用均以 `ProjectSnapshot` 为核心真相；
2. SQLite 任务、状态事件和任务日志形成可恢复、可解释的执行历史；
3. 运行队列、Agent 步骤、审校问题、修章动作、成本和日志在同一工作区完成；
4. 任何生成、重试、重跑、取消或批量动作都先形成明确意图，再由用户确认；
5. 失败任务显示“发生了什么、能否恢复、从哪里恢复、下一步做什么”，不只展示原始报错；
6. `/monitor`、`/chapters/maintenance`、`/tasks`、`/pipeline` 最终都兼容进入 `/production`。

## 社区项目与组件决策

- 参考 [Temporal](https://github.com/temporalio/temporal) 的持久任务、租约恢复和追加式 Workflow History 思路：当前状态来自任务记录，过程来自不可变事件，不用内存日志反推任务状态。
- 参考 [Trigger.dev](https://github.com/triggerdotdev/trigger.dev) 的运行列表、详情追踪、重试/取消、批量动作和 human-in-the-loop 设计：先选运行或问题，再在详情区审阅并确认动作。
- 参考 [Langfuse](https://github.com/langfuse/langfuse) 的 trace → span → generation 信息层级，但不引入外部观测服务；本地任务 → 状态事件 → Agent 日志已足够。
- 继续复用 `@tanstack/vue-virtual@3.13.34` 虚拟化长任务和问题列表，复用 `splitpanes@4.1.2` 构建列表/详情工作区。
- 不引入 Temporal、Trigger.dev、Langfuse SDK 或第二套队列。现有 SQLite 任务状态机已具备幂等键、claim、lease、heartbeat、checkpoint 和恢复能力，引入完整平台会制造新的部署与状态真相源。

## 非目标与安全边界

- 本阶段不会由自动化测试或页面加载自动触发小说生成、续写、审校、重写、重跑门禁或批量任务。
- UI 中的生产动作必须经过“建立意图 → 展示影响范围 → 用户确认 → 调用 API”的流程。
- 不伪造通用“重试任务”能力；只有后端已有明确恢复语义的任务才显示恢复动作。
- claim token、原始文件路径、配置密钥、内部堆栈和未经本地化的状态码不得进入普通 UI。
- 运行时内存日志只是实时补充；任务状态与恢复判断必须来自 SQLite。
- 不在本阶段清空用户数据；Phase 7 使用用户已授权的项目级重置流程。

## 实施清单

### 任务 1：补齐持久任务历史与日志

- [ ] 为 `TaskRepository` 增加项目作用域的状态事件查询，按事件 ID/时间稳定排序。
- [ ] 为 `TaskRepository` 增加任务日志追加和查询；日志必须关联合法任务并限制长度。
- [ ] 任务进度事件在更新 checkpoint 的同时持久化结构化日志，不再只进入内存环形缓冲。
- [ ] 对外任务 DTO 清除 claim token，并将 task type、status、reason、checkpoint 转成稳定字段。
- [ ] 覆盖跨项目隔离、事件顺序、日志裁剪、未知任务和租约恢复测试。

### 任务 2：建立统一生产工作区读模型

- [ ] 新增 `ProductionWorkspace` 领域契约和 `/api/production/workspace`。
- [ ] 响应以完整 `ProjectSnapshot` 为核心，附加近期任务、状态事件、任务日志和归一化审校队列。
- [ ] 所有进度数字直接取 snapshot，不由前端或旧 factory dashboard 重新计算。
- [ ] 任务摘要区分运行、排队、暂停、成功、失败、取消，并给出可恢复性和本地化原因。
- [ ] 服务读取失败时返回分区级错误，不把某个损坏质量报告变成整个生产中心 500。

### 任务 3：归一化质量问题与修章建议

- [ ] 从质量报告、checkpoint、批量重试和外审记录构建统一 review item。
- [ ] 将检查 code 映射为稳定中文标签、严重级别、分数、证据和建议动作。
- [ ] 同一章节的质量报告和流水线告警合并展示，保留多个 blocker，不重复计数。
- [ ] 无法解析的报告显示“报告损坏”，不得静默当作通过或直接暴露路径。
- [ ] 审校汇总、问题列表和 `ProjectSnapshot.quality_summary` 的通过/失败口径一致。

### 任务 4：构建生产中心主界面

- [ ] 新增 `/production`，顶部只展示正文进度、运行/排队、质量阻断和累计费用。
- [ ] “运行”页采用虚拟任务列表 + 详情区，展示 checkpoint、尝试次数、心跳和追加式状态时间线。
- [ ] “审校修复”页采用虚拟问题列表 + 详情区，集中显示问题、证据、建议和章节入口。
- [ ] “费用”页整合成本摘要与模型调用；“日志”页整合 Agent 实时日志与接口日志。
- [ ] 运行/问题选择写入 URL query，刷新和深链后仍保持上下文。
- [ ] 1440×900 和 1100×720 下无页面横向溢出，列表与详情独立滚动。

### 任务 5：建立安全的生产与修复动作

- [ ] 继续写书、批量生产、重试审校、重跑门禁、批量重写和取消任务均先进入确认对话框。
- [ ] 对话框显示动作类型、目标章节、预计影响和可撤销性；点击入口本身不得调用 API。
- [ ] 仅对已有 checkpoint/后端恢复接口的任务显示“恢复”，否则提供修稿、设置或日志入口。
- [ ] 批量动作在提交前再次解析选中范围，禁止混入不兼容状态的章节。
- [ ] 动作成功后刷新生产工作区；失败保留当前选择并给出用户可执行的下一步。

### 任务 6：收敛路由与删除重复页面

- [ ] `/monitor` 重定向到 `/production`，保留旧 tab 的语义映射。
- [ ] `/chapters/maintenance`、`/tasks`、`/pipeline` 重定向到 `/production?tab=reviews|runs`。
- [ ] 项目快照 next actions、批量暂停横幅、概览阻断、命令面板和书库待处理链接统一指向生产中心。
- [ ] 删除不再引用的 `MonitorView`、`ChapterMaintenance`、旧 tab shell 和重复修章页面逻辑。
- [ ] 保留可复用的日志、费用和批量运行组件，但移除其中对旧路由和重复状态的依赖。

### 任务 7：确定性夹具与自动化验证

- [ ] E2E 夹具生成运行、失败、成功任务及状态事件/日志，但不执行任何模型或流水线。
- [ ] 后端覆盖生产工作区契约、质量归一化、项目隔离和损坏输入。
- [ ] 前端单测覆盖筛选、状态本地化、动作可用性和路由兼容。
- [ ] Playwright 覆盖生产概览、任务选择、事件历史、审校筛选、动作确认、旧路由重定向和费用/日志切换；不得确认真实生成动作。
- [ ] 使用浏览器在 1440×900、1100×720、明暗主题下检查布局、键盘、URL 恢复和控制台。
- [ ] 运行完整后端、前端单元测试、生产构建、bundle、Electron、显式 E2E 和生产依赖审计。

## 完成标准

- 普通用户只需进入一个生产中心即可回答：现在运行到哪、为什么停、哪章有问题、如何恢复、花了多少。
- 项目进度和阻断不再由多个前端组件分别推导。
- 任务状态在进程重启后仍可从 SQLite 恢复，并可查看状态历史。
- 同一质量问题不在概览、章节维护和质量报告中重复形成不同口径。
- 所有有副作用的生产动作都经过明确确认，自动化验收不会触发真实生成。
- 旧生产/监控/维护 URL 可兼容访问，但没有重复页面实现。
- 页面无横向溢出、深色主题一致、完整质量门禁通过。
